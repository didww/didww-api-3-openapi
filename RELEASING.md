# Releasing a new document

The published document, `openapi/v3_api.json` and `openapi/v3_api.yaml`, is **built** from one
generated source per DIDWW service, kept in `openapi/sources/`:

| Source | Service | Generated by |
|--------|---------|--------------|
| `api.json` | `api.didww.com` | `bin/v3_api_openapi` in the platform repository |
| `voice_in.json` | `api-vin.didww.com` | the Voice IN service's generator |
| `voice_out.json` | `api-vout.didww.com` | the Voice OUT service's generator |
| `sms.json` | `api-sms.didww.com` | the SMS service's generator |

Every source is generated by its service's own integration suite, which drives the live endpoints;
nothing in this repository writes or edits a source. `scripts/build.mjs` assembles the published
document from them and fails when they disagree: a different version name, a shared component that
differs between two sources, a path two services both serve whose operations cannot be folded into
one. A source the repository does not hold yet is simply absent: the build takes the ones present.

```bash
npm ci          # once: the pinned build and lint tools
npm run build   # sources → openapi/v3_api.json + openapi/v3_api.yaml
npm test        # the build script's own tests
npm run lint    # Redocly over the sources and the published document
```

## Two branches

- **`main`** holds the version customers are served. Its raw URLs are stable and never show a version
  no API key can reach.
- **`prerelease`** holds the next version while it is prepared. It is long-lived: it is never deleted
  and never re-created.

Both are protected: a pull request is required and the `validate` job of the `Validate` workflow must
pass. Every merge is a merge commit (squash and rebase merges are disabled), so the two branches share
their history.

## Preparing a version

1. **Open the version.** The platform's pull request to `prerelease` carries `VERSION` of the coming
   version and `openapi/sources/api.json` generated from the platform's release branch of that version,
   with the production configuration, plus the rebuilt document. The version name in `info.version`
   comes from the platform configuration — a local configuration carrying a different date for the
   version silently stamps that date all over the source. No other source opens a version: before the
   main source of it is in, the others have nothing to be consistent with. Once `prerelease` holds service
   sources of the released version, the same pull request also carries each of them regenerated with
   its service's version constant set to the new name, as a rename does (step 3): every source must
   carry the version in `VERSION`, even one whose service did not change.

2. **Add or regenerate a source.** A pull request to `prerelease` replaces
   `openapi/sources/<service>.json` with the file its generator wrote, runs `npm run build` and commits
   the rebuilt `openapi/v3_api.*` in the same pull request. Its description says what the source adds
   or changes in the API.

3. **Rename the version, or change a shared artefact, in one pull request.** When the release date of a
   version is confirmed, `VERSION` and every source change to the new name together, in one pull
   request; the same holds for a change to anything the sources share (the error object, the bearer
   scheme, the file-endpoint headers, the shared prices operations). A pull request that changes one
   source alone fails the cross-source checks and cannot merge.

4. **Keep the branches in step.** Whenever something lands on `main` while a version is open — a fix to
   the build or CI, a regeneration of the released version — merge `main` into `prerelease` in a pull
   request that keeps `prerelease`'s `openapi/sources/*` and `VERSION`, and rebuild the document.

## Releasing

When the application releases of every product in the version are in production:

1. Open a pull request from `prerelease` to `main`; its description lists what the version adds or
   changes, per service. Merge it with a merge commit.
2. Tag the merge commit with the version date and push the tag:

   ```bash
   git tag -a "$(cat VERSION)" -m "DIDWW API v3 $(cat VERSION)" <merge-commit>
   git push origin "refs/tags/$(cat VERSION)"
   ```

   The tag is what keeps earlier documents reachable — `openapi/` on `main` only ever holds the
   released version.

After the merge `prerelease` equals `main` and simply stays; the next version's first pull request
targets it.

**A tag names an API version, not a moment.** When the document of the released version is regenerated
— the API did not change, the description of it got better — the regenerated source reaches `main`
through a pull request, the version's tag moves onto its merge commit (`git tag -f -a`,
`git push --force origin refs/tags/<version>`), and `main` is merged into `prerelease` (step 4 above).
Leaving the tag behind would keep handing out a document that is known to describe the same version
worse. A tag only ever stops moving when the version it names stops being the one `main` holds.

CI tests the build script, lints every source and the published document, rebuilds the document from
the sources and checks that it matches the committed one, that the JSON and YAML formats agree and that
`VERSION` matches every source. It cannot tell whether a source is up to date with its service: that is
what each service's generating suite is for.
